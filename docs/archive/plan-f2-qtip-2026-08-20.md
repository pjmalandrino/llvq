# F2 — Le bras QTIP : plan d'exécution (2026-08-20)

> **Pourquoi maintenant.** Le panel de relecture simulé (2026-08-20) a fait de
> cette absence le moteur de son « Major Revision » : *« le papier avoue que
> QTIP est "the single most valuable missing measurement" tout en prouvant
> qu'ajouter un bras coûte des centimes »*. La motivation du papier (« is
> reported slower than QTIP's kernel ») est **héritée** du papier LLVQ
> d'origine et jamais reproduite. Ce plan la transforme en mesure — ou en
> blocage technique documenté, ce que l'expert accepte aussi (« justifier
> techniquement pourquoi le portage est impossible, pas seulement coûteux »).

## 0. Les faits de reconnaissance (établis le 2026-08-20, lecture seule, 0 $)

| fait | valeur | conséquence |
|---|---|---|
| licence de `Cornell-RelaxML/qtip` | **GPL v3** | 🚨 **pas de vendoring** — notre dépôt est MIT/Apache-2.0. Le code QTIP est récupéré **au moment du job** (commit épinglé + sha256 vérifié), jamais commité ici. Contraste : le bras AWQ était MIT, d'où son vendoring. |
| commit épinglé | `e90c6688c8dfae326a3a81b5eb032db7c6680ec0` (2025-06-22) | toute récupération job-time cite ce SHA et vérifie le hash de l'archive |
| structure de `qtip-kernels/src/` | `inference.cu` (kernels) **séparé** de `qtip_torch.cu` + `wrapper.cpp` (glue torch) ; `test.cu` + `Makefile` = chemin de build sans torch existant | le kernel est extractible ; seule dépendance torch dans `inference.cu` : `#include <c10/cuda/CUDAStream.h>`, à neutraliser au build (sed job-time — modification à la compilation, pas une redistribution) |
| le kernel | `__global__ kernel_decompress_matvec<L,S,R,V,M,N,K>(float* out, const uint32_t* compressed, const half2* x, const half2* codebook)` — **un seul**, templaté | 2 bits = `L=16, S=9, R=2, V=1`. **M, N, K sont des paramètres template** → une instanciation par forme de projection (~7 formes distinctes au 4B), générée par un fichier de glue à nous |
| lancement | grid 128 × block 1024 ; **LUT codebook en shared memory : 64 KiB** (`1<<(9+5+1+1)`) | > 48 K par défaut → **opt-in dynamique requis**, exactement la danse déjà maîtrisée sur le kernel de rotation (§limitations du papier) |
| contraintes de formes | `M % 16 == 0`, `K % 16 == 0`, `N == 1` | ✅ toutes les dims du 4B passent (2560, 4096, 1024, 9728) ; pas de queue côté QTIP — asymétrie de comptabilité à déclarer, comme pour AWQ |
| sortie du kernel | `float*` (accumulation f32) | le seuil de vérification est celui de NOS bras (1e-5·Σ|w·x|), pas le seuil relâché f16 d'AWQ |
| headers | `<cuda/pipeline>`, `<mma.h>` | NVRTC douteux sur libcu++ → **compiler par nvcc → cubin au démarrage du job**, chargé par cudarc (qui sait charger un cubin). Pas de NVRTC pour ce bras. |

**Deux découvertes qui simplifient tout :**
1. **Le contenu de la LUT n'a aucune importance pour le chrono ni pour
   l'exactitude relative** : le décodage est un accès LUT sans branche
   dépendante des données. Une LUT arbitraire (gaussienne) + un buffer
   `compressed` aléatoire valide + **notre** décodeur de référence écrit
   d'après la spec du format = vérification f64 ligne à ligne fermée, sans
   exécuter une ligne de Python QTIP. (Notre implémentation de l'algorithme
   de référence est notre code — le droit d'auteur couvre l'expression, pas
   l'algorithme.)
2. Le bras est donc **un pur test de vitesse + un pur test d'exactitude
   mécanique**, comme AWQ : aucune revendication de qualité, payload
   synthétique, déclaré comme tel.

## 0bis. ✅ P0 EST FAIT (2026-08-20, 0 $) — et il corrige trois points du §0

Journal : [`mesures/f2-p0-recon-2026-08-20.txt`](mesures/f2-p0-recon-2026-08-20.txt).
Livré : `llvq-cuda/src/qtip_host.rs` (codec + 14 tests, **29 mutants tués sur 31**,
les 2 survivants déclarés équivalents dans l'en-tête), `ops/fetch-qtip.sh`,
[`qtip-provenance.md`](qtip-provenance.md).

**LE FORMAT EST RÉSOLU, ET IL L'EST SANS CARTE.** Grille de tuiles 16×16
row-major ; chaque tuile est un registre à décalage **circulaire** de 512 bits
(32 u16, MSB-first) ; l'état *s* = fenêtre 16 bits aux bits `[4s, 4s+16)`
**modulo 512** ; décodage `h = ((s+1)·s) & 0xFFFF`, index `(h>>6) & 0x1FF`,
signe au bit 15 **sur le premier élément seulement** ; poids plat `f = i·16+j`
→ état `f/2`, élément `f%2`. **2,0000 b/poids exactement.**
**Quatre implémentations indépendantes concordent** : le CUDA lu, une formule
Python directe, une transcription de leur `unpack_trellis` (200/200 tuiles
aléatoires), et le codec Rust — dont le vecteur épinglé a été recalculé contre
la transcription.

🕳️ **Trois points du plan du matin étaient inexacts, et c'est ce que P0 sert à
trouver :**

1. **« Le layout est le risque n°1, conçu pour échouer bruyamment en P2 »** —
   il se résout **intégralement sur le Mac pour 0 $**. Leur chemin de référence
   pur PyTorch (`get_hatW`, sans GPU) et leur chemin noyau (`get_hatW_kernel`)
   décodent le **même** buffer et sont traités comme interchangeables par
   `cache_hatW` : le chemin CPU **définit** donc le layout du noyau. Le job P2
   garde son utilité (il confirmera sur carte), mais il ne porte plus le risque.
2. **« `<cuda/pipeline>` et `<mma.h>` interdisent NVRTC, donc nvcc → cubin »** —
   comptage fait : **zéro usage** de l'un comme de l'autre (le MMA passe par de
   l'asm PTX inline), idem `using namespace nvcuda` et les macros `TORCH_CHECK`
   jamais développées. Le patch tombe à **4 lignes mortes** et NVRTC redevient
   plausible. ⚠️ **Non mesuré** — à confirmer en P2.
3. **« sans exécuter une ligne de leur Python » présenté comme une contrainte de
   licence** — c'était une confusion de ma part. La GPL contraint la
   **distribution**, pas l'usage. C'était un choix de simplicité ; il se trouve
   qu'on n'en a pas eu besoin.

**Ce qui reste ouvert après P0**, et qu'aucune lecture ne tranchera : la liaison
NVRTC ↔ template (le noyau est `__global__ static` templaté, son nom mangé doit
être retrouvé — name expressions, ou un enrobage à écrire), l'opt-in 64 Kio sur
la carte, et **toute vitesse**. Reste aussi à faire côté hôte : le décodeur
device, l'enregistrement du bras dans `arms.rs`/`planesbench.rs`, et le test
miroir `qtip_decoder_matches_rust.rs`.

🔎 **La liaison NVRTC ↔ template, qui était le point ouvert, est résolue** :
cudarc résout par nom et un `__global__ static` templaté n'en a pas, donc
l'extraction le réécrit en `__device__` et **nos** shims `extern "C"` portent
le nom. Le `__launch_bounds__` migre sur les shims.

🆕 **Et un déblocage d'outillage qui dépasse F2** : `ops/devtools/nvcc`, un
`nvcc` factice qui ne compile rien. `cargo check` ne compile ni ne linke de
code device — il ne bute que sur la sonde de version de `cudarc/build.rs` — donc
ce stub suffit à **typechecker tout l'arbre gaté `cfg(linux)` depuis le Mac**.
C'est exactement le trou qui a laissé `DISPLAY_NAMES` sept littéraux trop court
pendant un jour. ⚠️ Cela reste un typecheck : NVRTC, les spills et l'exactitude
ne s'établissent que sur carte.

**Ce qui reste ouvert, et qu'aucune lecture ne tranchera** : que NVRTC accepte
le texte du noyau (asm PTX inline, `__shfl_sync`, `__byte_perm`), l'opt-in
64 Kio sur la carte, et **toute vitesse**. `HAS_KERNEL[QTIP]` **reste `false`**
et ne basculera que dans le commit qui montre une compilation device réelle —
P2.

## 1. Architecture du port (résumé)

```
[job-time]  git clone --depth 1 (SHA épinglé) → sha256 vérifié
            sed: neutraliser l'include c10 dans inference.cu
            notre glue .cu (À NOUS, commitée) : #include "inference.cu"
              + instanciations explicites des ~7 (M,K) à R=2
            nvcc -cubin -arch=sm_89 → qtip.cubin
[planesbench] cudarc charge le cubin ; opt-in smem 64 KiB ;
            packing Rust (buffer aléatoire valide, layout tuiles MMA 16×16) ;
            référence Rust f64 (décodage LUT + signe, d'après la spec) ;
            vérification 1 105 920 lignes AVANT tout chrono ;
            bras dispatché dans les mêmes rounds que les 7 autres.
```

Comptabilité d'octets du bras : **2,0 b/poids** (payload seul ; LUT 64 KiB =
constante résidente, exclue comme nos tables de classes — même convention,
déclarée). Borne d'octets : 16/2,0 = **8× FP16** — le plafond le plus haut de
la table ; la question que le bras pose est *quelle fraction* il en convertit.

## 3. Risques, par ordre de probabilité

1. **Layout du buffer `compressed` mal rétro-ingéniéré** → la vérif f64 de P2
   échoue. C'est le risque n°1 et il est *conçu pour échouer bruyamment* : la
   vérification précède tout chrono. Mitigation : `test.cu` du dépôt QTIP
   documente le layout par l'exemple ; P0 le lit en premier.
2. **nvcc absent ou trop vieux dans l'image** → vérifier dans P0 le
   Dockerfile CUDA (l'image compile déjà les kernels candle) ; sinon,
   pré-compiler le cubin dans une image dérivée, SHA épinglé.
3. **`cuda::pipeline` exige un flag de compilation particulier**
   (`--std=c++17`, `-arch` exacte) → P2 est précisément le job qui le dit,
   pour 0,2 $.
4. **La perf QTIP dépend d'un tuning (BLOCK_COUNT=128) calibré pour une
   autre carte** → on mesure le kernel *tel que livré*, comme AWQ (« ported
   unchanged — its own grid ») ; c'est la règle du bras compétiteur, elle
   est déjà écrite dans le papier.
5. **GPL : le patch job-time est-il une « modification » problématique ?**
   Non distribuée, donc hors du déclencheur copyleft ; notre dépôt ne
   contient que la glue (à nous) et le script de fetch. Le papier cite QTIP
   normalement.

## 4. Ce que chaque issue donne au papier (pré-écrit, à affiner en P1)

- **QTIP convertit ≥ ~85 % de sa borne** (comme AWQ ses 88 %) : la phrase
  « slower than QTIP's » héritée devient un fait mesuré chez nous ; notre
  65 % est encadré par DEUX compétiteurs ; le « what a successor should
  attack » de la conclusion gagne son deuxième point d'appui.
- **QTIP convertit ~60-70 %** (comme nous) : le gap AWQ↔lattice se re-lit
  comme « GEMM-format vs codebook-format », un résultat NEUF et publiable.
- **QTIP sous ~50 %** : la motivation héritée était fausse dans notre
  harnais — se publie aussi, avec la réserve « tel que livré, tuning
  d'origine ».
- **Blocage technique** : une phrase précise en limitations, la tentative
  journalisée. Le papier reste soumis à l'heure.
