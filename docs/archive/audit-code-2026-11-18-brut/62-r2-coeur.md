### R2-SRC-01 Un code-livre `L1` passe le parseur de `smoke` puis fait paniquer le chercheur au premier bloc
- Gravité : mineure
- Confiance : CONFIRMÉ
- Où : `llvq-search/src/generic.rs:805` (`sections.push((self.odd_flat[0].bound, usize::MAX))`) ; `llvq-search/src/generic.rs:403-408` (filtre par niveaux) ; `llvq-llm/src/bin/smoke.rs:290-312` (garde) et `:297-299` (commentaire) ; `llvq-llm/src/bin/smoke.rs:1726-1729` (le test qui déclare `leech1c6L1` « searchable ») ; `llvq-quant/src/quantizer.rs:459-461` puis `:560` ; `llvq-llm/src/calib.rs:1424-1434`.
- Fait : `BallSearcher::with_level_cap(1)` ne garde qu'une classe sur 383 : la classe paire (±2²⁴), coquille 6, un seul niveau. Aucune classe impaire n'a un seul niveau (*computed*, recomptage des 383 classes avec les règles de `classes.rs` : L1 = 1 paire, 0 impaire ; L2 = 18 + 18 ; L3 = 80 + 101 ; L4 = 198 + 154 ; L5 = 226 + 157). `odd_flat` est donc vide, et `nearest_by` lit `self.odd_flat[0]` sans garde à la ligne 805, avant toute boucle. `smoke` refuse un code-livre vide, mais `class_count(m, 1)` vaut 1 pour m ≥ 6 : `leech1c6L1` à `leech1c13L1` sont acceptés. Le test `an_empty_codebook_is_refused` l'affirme même : « Shell 6 is where a single class appears — degenerate but searchable, so it stays legal ».
- Scénario : `smoke … leech1c13L1 …`. Le parseur accepte, `calib.rs` construit `LeechShapeGain::with_caps(gain, 13, 1)`, le modèle se charge, la calibration du premier bloc tourne, puis le premier `quantize` appelle `nearest_angular` et panique sur « index out of bounds: the len is 0 but the index is 0 ». Sur HF Jobs, c'est un run payé perdu après le chargement. Accessoirement, `shell_bests` sous L1 panique aussi, dans `materialize` (`unreachable!("every shell 2..=13 is non-empty")`, `generic.rs:887`) pour les 11 coquilles sans classe ; seul `nearest_ball13` (sans appelant, QUA-09) l'atteint par ce chemin.
- Touche : encodeur (Ball, non servi), outillage. Aucune taille publiée : les trois fichiers servis sont Tetra.
- Correction proposée : à `generic.rs:805`, remplacer par `if let Some(h) = self.odd_flat.first() { sections.push((h.bound, usize::MAX)); }` ; la lecture `self.odd_flat[0].bound` de la ligne 814 n'est alors atteinte que si la section existe. Corriger le commentaire de `smoke.rs:297-299` : « L1 vide le code-livre jusqu'à la coquille 5 ; à partir de 6 il garde la seule classe (±2²⁴) ». Si l'opérateur préfère refuser L1, le refus va dans `parse_codebook` et le test `an_empty_codebook_is_refused` change d'assertion.
- Effort : S
- Risque de la correction : nul. Ni format, ni carte d'index (l'index reste celui de la boule entière), ni token servi, ni fichier épinglé. Le chemin L ≥ 2 ne change pas : `odd_flat` n'y est jamais vide.
- Vérification proposée : test neuf dans `llvq-search/tests/g2c_reference.rs`, `a_one_level_codebook_is_searchable` : `BallSearcher::with_level_cap(1)`, 20 blocs gaussiens, `nearest_angular` rend `shell == 6`, toutes les coordonnées à ±2, un point de Λ₂₄ ; `nearest_scaled(&s, &x, 0.5)` rend l'origine ou cette classe. Mutant : remettre `self.odd_flat[0].bound` à la ligne 805, le test panique.

### R2-SRC-02 Le lecteur Ball ne borne l'index que par sa largeur : un cap 12 décode en silence des points de la coquille 13
- Gravité : mineure
- Confiance : CONFIRMÉ (fichier corrompu ou forgé seulement)
- Où : `llvq-artifact/src/format.rs:603-616` (`index_width`, bras Ball) ; `format.rs:409` (`Codebook::decode` → `Indexer::decode`) ; `format.rs:1498-1508` (`decode_codes`, seul refus `IndexOutOfRange`) ; `llvq-quant/src/quantizer.rs:996-1000` (`index_bits`) ; `llvq-search/src/index.rs:334-341`.
- Fait : pour un enregistrement Ball, le lecteur prend `index_bits(shell_cap)` bits par index, puis décode par l'`Indexer` de la boule entière Λ₂₄(13). Le seul refus est `idx > N13`. Rien ne compare l'index à N(cap), le nombre de points du code-livre que l'enregistrement déclare. `index_width` refuse un cap > 13 mais accepte 0 et 1 : `index_bits(0)` et `index_bits(1)` valent 1 (`.max(1)` sur une boule vide). Les écrivains ne contrôlent aussi que la largeur (`IndexTooWide`).
- Scénario : chiffres *computed* par les formules de `classes.rs` (somme exacte N13 = 280 974 212 784 720 retrouvée). Cap 12 : N(12) = 111 043 117 458 000 sur 47 bits ; les 29 694 370 897 327 index de N(12) + 1 à 2⁴⁷ − 1, soit 21,1 % du champ, se lisent sans erreur et rendent des points de la coquille 13. Même trou à chaque cap sous 13 (cap 11 : 42,4 % du champ de 46 bits ; cap 2 : 25,0 % de 18 bits). Cap 13 : les 500 763 925 935 index au-delà de N13 sont bien refusés. Un enregistrement `shell cap 1` avec l'index 1 se lit et rend le premier point de la coquille 2, hors d'une boule déclarée vide. Le format promet le refus de ce qu'il n'a pas pu écrire (`hostile_files.rs`) ; l'encodeur cap 12 n'écrit jamais ces index, et la carte les décode quand même (les tables d'exécution couvrent les 383 classes).
- Touche : format (lecteur Ball). Les fichiers publiés sont Tetra : le bras Tetra lit 47 bits dont chaque valeur est un label, il n'est pas concerné.
- Correction proposée : dans `llvq-quant/src/quantizer.rs`, sortir de `index_bits` une `pub fn ball_size(cap: u32) -> u64` (le `n` qu'elle calcule déjà) et la réutiliser. Dans `format.rs::index_width`, bras Ball, refuser `shell_cap < 2` en `Error::Inconsistent`. Dans `read_lattice_body`, pour `kind == Ball`, calculer `ball_size(shell_cap)` une fois et refuser dans la boucle tout `idx > max` en `Error::IndexOutOfRange { name, index }` ; même contrôle dans `write_codes` et `code_stream`, à côté d'`IndexTooWide`.
- Effort : S
- Risque de la correction : faible. Aucun octet écrit ne change. Elle touche le lecteur du format : suite complète en release avec l'archive Ball scellée `~/llvq-q4b.llvq` (cap 12), dont tous les index viennent de l'encodeur cap 12, donc sont ≤ N(12). Pas de carte d'index, pas de token servi.
- Vérification proposée : deux tests dans `hostile_files.rs`. (1) Écrire `small_matrix()` (cap 12) avec l'index légal N(12) = 111 043 117 458 000, puis réécrire dans le flux de codes (MSB-first) cet index en N(12) + 1 : `Err(IndexOutOfRange)` attendu, `Ok` et un point de coquille 13 aujourd'hui. (2) Un enregistrement Ball `shell cap 1`, index 1 : `Err` attendu. Mutant : retirer le contrôle `idx > max`, le test (1) repasse à `Ok`.

## Le chemin Tetra servi : ce qui est vérifié, et ce qu'aucun test ne garantit

Vérifié à la lecture, sans constat. Je ne redis pas ce que 06-numerique.md a déjà vérifié (bijection, `stride_u32`, multinomiales u128).
- Mot de 48 bits (`word.rs`) : dix champs, largeurs puissances de deux, pavage exact de 0..48. Au décodage, `i1 ≤ 2047` lit `rows[2048·r + i1] < 4096` ; `i2 ≥ 1240` lit `rows[2048 + i2 − 1240] ≤ rows[2855]`. L'encodeur rend `i2 = pos2 % 2048 + δ·1240`, l'inverse exact sous la forme close épinglée. `join` refuse un champ trop large au lieu de le tronquer.
- Encodeur (`encoder.rs`) : coûts en u32 au plus 8·961 = 7 688 ; aucune soustraction non signée ne passe sous zéro (`j ≠ j2` toujours, car `j0 ≠ j1`) ; indices des tables à cinq entrées dans 0..4 ; `z` borné à ±10⁶ avant `as i32`. Pour l'échelle, `s0 ≤ 0,3218·max|x|` et `s0·1,14` reste fini ; le produit `ALPHA·m·unit_norm` déborde seulement au-dessus de `f64::MAX/1,58` et retombe alors sur le chemin « unit-max ». `Scratch` est réécrit en entier à chaque passe. L'amorçage `u0` par l'autre parité et les bornes inférieures n'élaguent rien qui puisse gagner strictement. Les ex aequo du repli sont impossibles, deux mots distincts donnant deux points distincts.
- Déterminisme : l'encodeur n'utilise que `+ − × ÷`, `sqrt` et `powi(2)`, ni libm transcendante ni FMA. Il est donc identique d'une machine à l'autre à entrée égale. L'entrée, elle, dépend de `faer` (NUM-03).
- `tetra48` : fenêtre du dernier bloc recalculée, `6n` octets pour n pair, `6n + 2` pour n impair, toujours sous `stride_u32·4`.
- `codebook.rs` : l'empreinte Tetra replie trio, 4 096 lignes, colonnes F₂, largeurs, partage 1240 et 66 décodages. L'ordre trio et la convention de signe de `val` sont donc couverts par les sondes.

Ce qu'aucun test ne garantit :
- **L'encodeur de production contre la règle du banc** n'est comparé que sur 2 000 blocs gaussiens à trois échelles, en release seulement (`llvq-bench/tests/tetra_encoder.rs:62-63`), avec un écart de coût toléré de 1e-9. Aucun test ne confronte l'élagage de `solve_parity` à une résolution sans élagage sur des blocs à queue lourde ou réels. Le test de taux (`the_join_solves_a_small_fraction_of_the_entries`) épingle un pourcentage, pas une réponse. Mon argument de lecture tient ; un test le rendrait opposable.
- **NaN sous `fast-linalg`** : `cholesky_lower` refuse NaN par nom (`linalg.rs:122-126`), mais le chemin payé appelle `faer`, et rien ne vérifie que `llt` refuse un pivot NaN. `calib.rs` ne garde pas H contre NaN. Depuis le lot 3, une `U` NaN serait arrêtée un bloc plus tard par `TetraShapeGain::quantize` (« non-finite weight »), avec un message qui nomme un poids et non le Hessien ; `LeechShapeGain` (Ball) n'a pas ce refus. Test proposé : `GptqFactor::new` sur un H à diagonale NaN doit rendre `Err` sous les deux features.
- **Le masque `TETRA48_SHELLS = 32`** : la constante Rust n'a aucun utilisateur, et le noyau masque `(n2 >> 4) & (TETRA48_SHELLS − 1)` avec sa propre copie (`llvq_pers.cuh:250`). Le maximum m = 26 vient d'un exemple, `tetrashell.rs`. La marge est réelle : au plus ‖y‖² = 152 par section sur les 4 096 lignes, les deux parités et les deux résidus, donc ‖y‖² ≤ 456 et m ≤ 28 < 32 (*computed*). Un test qui l'affirme sur la table garderait un futur changement de bornes.
- **Les tables de rotation d'un OS à l'autre** : `SplitMix64::next_gaussian` passe par `ln` et `cos` de la libm du système, et `Rotation::small` (Q_odd, jusqu'à 19×19 pour 9 728 = 19·512) peut différer de quelques ulps entre l'encodeur Linux et un lecteur macOS. Aucun test n'épingle ces bits. L'effet est négligeable une fois en f32. Je le note parce que rien ne l'exclut.
