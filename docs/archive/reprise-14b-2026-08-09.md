## 4. Les deux échecs de scellement, et leurs causes

**① `libcuda.so.1` introuvable** — `seal` était bâti avec `--features cuda`
comme les autres binaires, donc lié à libcuda, absent d'une flavor CPU. Or
`seal.rs` code `Device::Cpu` en dur. **Corrigé** : `ops/Dockerfile.cuda` le
construit maintenant sans feature, image republiée.

**② OOMKilled (exit 137) sur `cpu-upgrade`, 32 Go, après 294 s.** Cause
structurelle : `seal` appelle `read_matrix`, qui **décode** — un
`ix.decode(idx)` par bloc, accumulé dans un `Vec<BlockCode>`. Sur le 14B :
~550 M blocs × ~100 o = **~55 Go de codes décodés en RAM**, plus les tenseurs
portés et les copies de shard.

⚠️ Mon estimation « pic ~15 Go » était fausse : j'avais vu le streaming shard
par shard du checkpoint sans voir que la moitié quantifiée, elle, est
intégralement décodée.

**Conséquence pour la suite** : le scellement exige une flavor à RAM.
`cpu-xl` (124 Go, 1,00 $/h) devrait passer, `cpu-performance` (256 Go,
1,90 $/h) est sûr. **Et à 32B ce serait ~130 Go décodés, donc
`cpu-performance` obligatoire** — à noter avant d'estimer ce run-là.

## 5. Ce qui reste, dans l'ordre

### ① Sceller (~1 à 2 $)

```bash
uv run ops/run.py bench \
  --image hf.co/spaces/Pier-Jean/llvq-runner-cuda \
  --flavor cpu-xl --any-flavor \
  --bucket Pier-Jean/jobs-artifacts --out-mount /out \
  --timeout 2h --name seal-14b \
  'export LLVQ_MODEL=Qwen/Qwen3-14B' \
  'seal /out/qwen3-14b-c12-3f21abde/qwen3-14b-c12.llvq /out/qwen3-14b-c12-3f21abde/qwen3-14b-llvq.bin' \
  'ls -la /out/qwen3-14b-c12-3f21abde/'
```

À vérifier dans son log : **163 tenseurs portés** (le 14B délie ses têtes,
`tie_word_embeddings: false` — établi par l'entrée `EXPECTED`) et une sortie
autour de **6,7 Go**. Un écart sur l'un ou l'autre veut dire que le
complément de tenseurs n'a pas ramassé ce qu'il fallait.

### ② Déquantifier l'AWQ (~0,20 $, parallélisable avec ①)

```bash
uv run ops/run.py dequant \
  --awq-repo Qwen/Qwen3-14B-AWQ --base-repo Qwen/Qwen3-14B \
  --bucket Pier-Jean/jobs-artifacts --name qwen3-14b-awq-deq \
  --flavor cpu-upgrade --timeout 4h
```

⚠️ **Pas de push vers un dépôt modèle** : depuis C5, `Checkpoint::fetch`
accepte un répertoire local, donc la campagne lit la sortie **depuis le
bucket monté**. Ça retire 29,5 Go de téléversement.

L'entrée `EXPECTED` du 14B est écrite et ses cinq contrôles passent
(`check` vert, cosinus mod 8 homogènes à 1e-4 — pas de permutation). Le
**tokenizer est identique** entre `Qwen3-14B-AWQ`, `Qwen3-14B` et
`Qwen3-4B` : l'empreinte de tokens est commune par construction.

### ③ Campagne 3 bras + dumps MMLU (~1,80 $, `l40sx1`)

Protocole du 4B et du 8B, à reproduire tel quel : `ppl 4096 12 cuda` et
`mmlu <modèle> cuda 40`, `LLVQ_DTYPE=f16` des deux côtés.

Trois bras : `Qwen/Qwen3-14B` (f16) · `/out/qwen3-14b-awq-deq` (AWQ déquantifié,
lu depuis le bucket) · `/out/…/qwen3-14b-llvq.bin` (scellé).

🚨 **Poser `LLVQ_MMLU_DUMP` sur les trois bras.** C'est la raison d'être de
l'instrument écrit ce matin : sans dump, l'écart n'est pas testable en
appariement et le rejeu sera dû une seconde fois. Puis `bin/mmlupair` sur les
trois CSV — gratuit, local, < 1 s.

### ④ Job de correction, 4 paliers (~0,75 $, `l40sx1`)

Quatre choses n'ont **jamais tourné ensemble sur une carte** : `Planes12x`,
la queue f16, la mémoïsation de rotation, le matvec segmenté. Mesurer par
paliers, pas d'un bloc — un désaccord de tokens sur l'objet complet ne dirait
pas lequel des quatre l'a causé.

| palier | bascule | critère |
|---|---|---|
| ① témoin | tout off | 128 tokens de référence |
| ② queue f16 (A7a) | automatique | tokens identiques à ① |
| ③ rotation hissée | `LLVQ_ROT_SHARE=1` | tokens identiques **et** 252 → 144 lancements |
| ④ `Planes12x` | `LLVQ_FUSED_LAYOUT=planes12x` | tokens identiques au bras dense |

⚠️ Pour ③, **ne pas réutiliser le critère fusé/dense** (« divergence au token
89 ») : les deux bras exécutent les mêmes noyaux avec les mêmes arguments,
seul le nombre de lancements change, donc les 128 tokens doivent être
**identiques**. Une rotation périmée se rangerait sous le critère laxiste.
Et lire la phase `blocs+norme` : sous ~0,3 ms d'écart, le lot ne se publie pas
et le défaut reste `off`.
