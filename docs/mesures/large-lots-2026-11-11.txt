==========================================================================================================================

1. WHAT SEPARATES A TREE PASS FROM A BATCH OF STREAMS
----------------------------------------------------
- K/V store. Every layer of Pers4eArgs carries one cache (Y.kc, Y.vc, cap positions), baked into the images at
  install. A row reads positions below pos0 from it and its tree positions from the slot buffer tk/tv through path.
  Streams need a cache each. The pool's layout [P][n_kv][cap][128] (batch.rs) matches the kernel's per-head layout,
  so a per-row slot base in p4t_attn_issue is enough. Small change.
- Masks. There is no mask tensor: a row's keys are the shared prefix plus its ancestors (path[r][..=depth[r]]). A
  stream is depth 0 with path[r][0] = r. Works as is once pos0 is per row. Small.
- Positions. RoPE and the attention length read pos0 + depth[r]: one pos0 for the launch. Streams need pos0[r], one
  array in Pers4tLaunch. Small.
- Cache write. The move phase copies n_move accepted rows into one cache at consecutive positions. Streams need each
  row written into its own slot at its own position. A loop rewrite of 15 lines. Small.
- Head. Each row gets its own argmax (L.slots, L.ring). Greedy only, as 4E. Sampling needs either the [R][vocab]
  logits (16 x 151,936 x 2 B = 4.9 MB a step, *computed*) read back or a device sampler. Medium, and not needed while
  serving is greedy.
- Host loop. spec_loop.rs drives one sequence (one pos0, accept along the path). A batch has no acceptance: every row
  is accepted. The scheduler already exists in llvq-runtime (BatchKv pool, admission by prefill_slot, a lone request
  back to 4E). The work is to swap that pool's step from tv_batch_gemm to the pass. Medium.
- Cache size. 4E's install fixes cap at 8,704 positions; the pool allocates 2,048 a slot. The images must point at the
  pool. Medium.
- Attention cost. Tree rows read one shared prefix, so 16 rows hit L2. Independent streams each read their own K/V
  from DRAM. This is the one part that may need a rewrite (see 2).
Verdict on 1: a kernel change of a day or two plus the pool integration. Not a rewrite at short context.

Longer context (*computed*, bandwidth floor at 864 GB/s, 147,456 B of K/V a position):
- A stream's K/V read a step: 0.302 GB at 2k (0.35 ms), 1.208 GB at 8k (1.40 ms).
- 16 streams at 2k add at least 5.6 ms a step: about 13.3 ms with copies, 1,200 tok/s aggregate, 75 a stream.
- 16 streams at 8k add at least 22.4 ms: at most about 530 tok/s aggregate, 33 a stream.
- The pass at 8k already reads 48.2 ms for one shared cache, against 6.15 ms for 4E (*measured*, M3); the cause is
  not established. Long-context batching through this pass is unproven and probably poor.

VRAM per added stream (*computed*):
- K/V: 0.302 GB at 2k, 1.208 GB at 8k (Grow(256) rounds up).
- Row buffers: 0.153 GB for the pass, fixed (loader); about 0.01 GB a row.
- Shared, paid once: weights and 4E 1.98 GB; copies 1.308 GB if used.
- VRAM per stream therefore falls with the batch (weights amortized). The copies are the one item that moves b/param:
  2.73 to about 5.3 whole model at 4.02e9 parameters (*computed*).

Latency a lone user sees:
- Alone, the pass gives 145 tok/s with copies and 105 without, against 224 on 4E. The engine must hand a lone stream
  back to 4E, as the pool does today.
- When a second user arrives, the first drops from 224 to 144 (copies) or 104 (no copies) tok/s, x0.64 or x0.46.
- A new stream's prompt still goes through the batch-1 prefill and stalls the others for its duration (35 s at 8k,
  ROADMAP), the open L22 problem.

3. QUALITY
----------
- The pass is not 4E's arithmetic: f16 weights with folded scales and its own sum order.
- GSM8K-200: 177 of 200 texts identical to 4E, 58,101 of 63,441 tokens before the first divergence; all 23
  divergences sit on near-ties (margin 0 or 0.0156). Grades: pass 167, 4E 166 (*measured*, SP6, SP8).
- The 8k pass leaves 4E's greedy at token 28 on a margin of 0.0156 (*measured*, M3).
- The paired perplexity gate (S2, +-0.12 % of 4E) has never run.
A served batch mode would have to re-gate:
- paired perplexity within +-0.12 % of 4E through the batch step at R = 1, 8, 16;
- row independence: a stream's tokens bit for bit the same whatever R, its slot, and its neighbours' contents and
  lengths (today's guards cover tree rows over one cache, not rows over separate caches);
- the switch: a stream that moves between 4E (alone) and the pass (batched) changes arithmetic mid-answer, so its text
  depends on load. Either accept this under the tolerance, as the GEMM pool does, or keep a stream on one arithmetic;
- GSM8K-200 paired against 4E, and one run at 8k.

4. IS IT WORTH AN EXPERIMENT NOW
--------------------------------
No. The operator's priority is single-user chat, and a batch engine never speeds up a lone user: it slows the first
user by a third or more as soon as a second one arrives. Under the b/param rule only the in-place pass is admissible,
and it ties the GEMM pool that is already on main. The lead becomes worth a run when an in-place 16-row pass costs 1.8
4E tokens or less (8 ms), which the memory axis needs anyway for speculation; the batch mode would then ride on that
work for a day or two of host code. The smallest experiment, if wanted anyway: a vtreebench arm with per-row pos0 and
per-row cache slots, depth 0, at R = 1, 2, 4, 8, 16 and contexts 62, 2k, 8k, a12 and a12ip, beside tv_batch_gemm at
the same B and 4E. Card time: about 20 min of load and install (N11: 1,211.6 s) plus 10 to 15 min timed, 30 to 35 min
of L40S, about $0.90 to $1.05 at $1.80/h (*estimated*). Host work before it: one to two days, $0.
