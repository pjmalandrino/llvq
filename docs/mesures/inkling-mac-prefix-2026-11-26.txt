THE DESIGN AS BUILT
  The save point is `b`, the last multiple of 512 tokens inside the static block. The block's end `L` is the common
  prefix of the request's ids and of the ids rendered from its leading system messages alone (same tools, same
  effort); here L is about 8,770 and b = 8,704. The first read is cut at b, which is a boundary of its 512-token
  pieces, so the read keeps its cuts and its bits; the state is written there, and the read goes on.
  The file (`llvq-runtime/src/prefix.rs`): magic, a JSON header with the key (format, family, model file sha256,
  sha256 of the running executable, backend, stack, piece, score rows, slot slack, where the bias is built), the
  tokens 0..b, the cache state (`llvq-llm/src/inkling/snapshot.rs`: per slot len, base, capacity, bound, keys and
  values held in their stored dtype, the four convolution states read back from the rings), then a digest: the sha256
  of the sha256 of each 64 MiB chunk (E1). Written to a temporary file in `<store>/prefix/`, mode 0600, then renamed.
  The load takes the longest file whose name carries this key and the sha256 of the prompt's first b tokens, with b
  past what memory keeps; checks the key field by field, the stored tokens one by one and the digest; then loads into
  a new cache (the old one dropped first). A refusal is logged by name and the prompt is read as without the cache.
  `llvq serve --prefix-cache on|off` (default on for Metal only) and `--prefix-cache-max` (default 4G, least recently
  used first). On a CPU build or a candle stack, `on` is refused by name; on CUDA it compiles and can be turned on.

WHAT THE READING DOES NOT SAY
  Nothing about a static block that changes inside its first b tokens (a date in the system prompt, say): it loads
  nothing, as P-e shows, and a new file is written for each version. The cap of 4 GiB holds two such files.
  Nothing about CUDA: off by default, type-checked only (linux-check.log).
  The in-memory path is unchanged: a new conversation on a server whose memory still holds 0..b (after a load) rolls
  back in memory, as before this lot. That rollback is not shown to give a cold read's bits when a bounded slot has
  moved its base since b (M5b suggests the extra masked keys change nothing; it was not measured on the real model).

AFTER THE REVIEW BEFORE THE MERGE (2026-11-26, commit 404e6a0)
  The key gained `files_sha256`: every file under the model's parts, as its canonical path, its size and its
  modification time. The key had carried the sha256 of the local file alone, which files sealed again at the same
  paths, or two releases of a pulled set, leave unchanged: a state saved by other weights would have been loaded.
  Files written before that commit are refused by name, on the key. A temporary file left by a write that never
  ended is removed by the eviction once it is an hour old. No measurement was run again: the read after a load is
  the code the gates above ran.
