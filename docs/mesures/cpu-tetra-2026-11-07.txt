THE 4B SERVED ON THE CPU WITHOUT DECODING ITS WEIGHTS: 8.65 TOK/S IN 1.86 GB AGAINST 0.71 TOK/S IN 10.6 GB, PERPLEXITY -0.0021 % OF THE DENSE f32 (2026-11-07)
==============================================================================================================================================================
Why:    a laptop without an NVIDIA or Apple GPU took the dense reconstruction (`sealed::load` on `Device::Cpu`), whose
        speed and memory had never been measured. This lot adds a CPU backend that reads the Tetra codes at every
        matvec (`llvq-llm/src/tetra_cpu.rs`, `fused_cpu.rs`) and puts it in the runtime in place of the dense path.
Cost:   $0. Apple M3 Max (12 P + 4 E cores, 64 GB), macOS 26.6.2, rustc 1.95.0, nice 10, LLVQ_THREADS and
        RAYON_NUM_THREADS at 12 or 4. The machine was shared with other sessions. The rates of the table below were
        re-read at 00:25-00:35 on 2026-11-08 under the exclusive lock /tmp/llvq-mac-bench.lock (flock(2), through
        locked/withlock.py since the Mac has no flock(1)), load 2.8 to 5.9; the earlier unlocked runs are kept,
        and the contended ones marked.
Object: qwen3-4b-sealed.bin, sha256 886391a8..., the store blob of `llvq pull qwen3:4b`.
Config: configs/qwen3-4b-tetra-e4.json (tetra48, embed q4, rot_share 1, fuse 0, kv f16, expanded, eager), the
        `cpu` entry `library.json` now carries.
Code:   base 529100a, the worktree of this lot uncommitted at measurement time. Binaries in binaries.sha256; the
        throughput runs c/d and the window-3 reading ran a cpurun built one edit earlier (the CLI's default dtype),
        same arithmetic.
Nature: *measured* for every rate, memory peak, token id and NLL; ratios and intervals *computed* by pair.py.
Raw:    docs/mesures/cpu-tetra-2026-11-07-brut/.

GATES
-----
  1. tetra_cpu::tests::decode_matches_the_reference: the table decode equals Tetra::decode_trio_order and
     Tetra::decode on 200,005 words (random, the origin, both gains, the mixed split's edges).
  2. tests/cpu_tetra.rs, 6 tests: the Tetra matvec against decode_matrix (f64 reference, f32 output) on five
     shapes (4B hidden 2560 with a tail of 16, down_proj's 9728, 4096, 240, a natural-basis 72), within
     2e-6 of sum|w x| per row, on every SIMD path of the CPU (scalar and NEON here, scalar and AVX2 on CI);
     19-row batches against single rows; the rotation left out is caught (> 1e-2); the candle adapter;
     int4 g128 against Int4Matrix::to_f32; the int4 g64 embedding's gather (bit for bit) and head (70 rows).
  3. Mutants of tetra_cpu.rs, 10 of 10 killed: NEON lane order, norm-table shift, trio permutation dropped,
     word phase, int4 nibble halves swapped, row scale dropped, bias dropped, mixed split, batch transpose,
     int4 pass offset. A first mutation run used a test filter that excluded tests/cpu_tetra.rs and read two
     survivors; it was discarded.
  4. Workspace: cargo test --profile ci -p llvq-llm -p llvq-runtime green (openapi.json regenerated for the new
     `config_cpu` field); cargo clippy --all-targets zero warnings on aarch64-apple-darwin, and on
     x86_64-unknown-linux-gnu through ops/check-linux-cuda.sh (the AVX2 path type-checks; it never ran here).

backend's matvec is the same in both runs; what differs is candle's CPU arithmetic in f16 around it (norms,
attention, softmax). Hence the runtime runs the CPU backend at f32, which is also the faster dtype there.

WHAT THIS DOES NOT SHOW
-----------------------
  - Nothing ran on x86. The AVX2 + FMA path compiles for x86_64 Linux and its tests run on the CI runner; no x86
    rate exists. No AVX-512 or VNNI path. Windows was never built.
  - The 8B and 14B never ran on the CPU path.
  - Memory at long context: the KV cache is f32 on this path, 288 KiB a position on the 4B (computed: 36 layers x
    2 x 8 heads x 128 x 4 B), 1.2 GB at 4,096 positions, twice the f16 cache.
  - The rates are one machine, shared, two repeats at most.
