WHAT CHANGED (commits bde0ed3, c000fbd)
  `llvq-llm/src/inkling/layers.rs`: `set_window_scores` (a switch for a process, off by default) and
  `AttnWeights::scores_window`. With the switch on, `scores` of a sliding layer hands over to it; the full layers
  (5, 11, 17, 23) keep `scores` as it was. Each chunk of query rows reads the keys and values from the first key its
  first row sees (`first_visible`, `(pos + 1).saturating_sub(window)`, the mask of `score_bias`) to its last row's
  own position; the bias is built for that range, the first row's position counted from the range's first key.
  How it narrows: once a call, then per chunk. One copy a call, as today's path makes one, of the keys any row of
  the call sees: from the first row's first visible key to the last key held (1,535 keys for a piece of 512 in a
  settled slot, against the 2,560 the slot holds, *computed*). The keys go row-major `[heads, S, d]` like the
  values, so a chunk's range is a view of each copy that candle's products read in place (the keys as a transposed
  operand, the mlx gemm's `nt` form); no copy is added a chunk. A chunk of 128 rows reads at most 1,151 keys
  (*computed*).
  `llvq-llm/src/bin/inkrun.rs`: `--attn-window full|narrow`, default `full`; the report's provenance names it.
  `llvq-llm/tests/inkling_window.rs`: gate D-i. `llvq-runtime` is not touched.
  Tree before the identity gates: `git status --short llvq-llm llvq-runtime configs` empty (all.log, first line).

PART E, THE DECODE: VOID
  After a long prompt a bounded sliding slot holds more than the window: it keeps `window + slack` = 2,048 positions
  and grows to `window + 2 * slack` = 3,072 before it drops its oldest (`KvBound::retain`, `settled_capacity` in
  layers.rs). The served decode does not read them: the one-row score kernel of `--attn fused+scores` takes only the
  visible keys, `llvq-llm/src/inkling/attn_scores.rs` line 193,
    let lo = window.map_or(0, |w| (pos + 1).saturating_sub(w));
  and its loops run from `a.lo` over `a.nvis` keys (lines 140 and 171). E has nothing to remove; no E run was made.

WHAT THE READING DOES NOT SAY
  That the arm keeps quality: equal greedy tokens over 32 steps on two prompts is the prereg's gate, not a
  perplexity band. Serving it would need the band the other class B switches carry; not run.
  Why the peak footprint rises 0.24 GB at 9,000 tokens. The copies a call are smaller and the score tensors of a
  chunk too; candle's buffer pool now holds buffers of other sizes, which may be it (*estimated*, not traced).
  That the gain holds on CUDA or the CPU, or with other piece and chunk sizes: one stack, one machine, arm B only.
  The runtime: unchanged, its first token not re-read.
  The share of the 19.1 s saved that is scores and copies: no profile run (`--prefill-phases`) in this lot.
