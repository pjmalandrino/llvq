2. VRAM AT 8,192 TOKENS
-----------------------
The speculative loop has never run past a few hundred tokens of prompt. specbench caps N at 1,024 and the tree pass
refuses positions past P4E_MAX_CAP = 8,704 (persist4e_cuda.rs:1683, served_decode.rs:32), so 8,192 + 256 fits.
  served 4E peak                                 5.95 GB   measured  pic-vram-8k-2026-11-08.txt:142 (5,671 MiB)
  plus the items resident during the prefill    2.74 GB   counted   1.308 + 0.153 + 1.193 + 0.085
  speculative peak, at the target's prefill      ~8.69 GB  computed  17.3 b/param
The drafter's own prefill comes after the target's. It grows the context cache to 16,384 positions, 0.340 GB
(computed, dflash.rs:535-547 doubles past 8,208), and uploads the prompt's taps as one [8,192, 12,800] tensor, 0.21 GB
in f16 then 0.42 GB in f32 (computed, dflash_spec.rs:126). Those come after the score tensors are freed to the pool,
so they should reuse that memory and not raise the peak (estimated, not measured). The prompt's taps cross the host,
0.21 GB of host RAM (model.rs:2810).

3. B/PARAM, WHOLE MODEL, TABLES INCLUDED (computed)
---------------------------------------------------
File bytes: the sealed file is 2.7320 b/param, 1,373.7 MB (docs/ETAT.md:32, sealed-8b-14b-2026-09-23.txt:32).
  (a) sealed file + drafter as today (2 B a parameter, 1,074.9 MB)
        4.870 b/param of the target; 4.296 per parameter of target plus drafter
  (b) sealed file + drafter at the served projection rate, 2.55 b/weight (spec-house.txt:5), 171.3 MB
        3.073 b/param of the target; 2.711 per parameter of target plus drafter
(b) is a rate, not an object: nobody has encoded the drafter, and its fc was moved to f32 because the taps reach 15,352
(dflash.rs:314-323). Its quality at that rate is unknown.
VRAM accounting of the weights: 3.88 GB, 7.72 b/param under (a); 2.86 GB, 5.69 b/param under (b).

The tree-tiled copies are a VRAM layout, not file bytes. The code builds them at install, on the card, from the words
already resident: one p4t_tile_words launch a projection (persist4e_cuda.rs:1503-1555). Nothing is read from the file
for them, so the sealed file does not change. They are held beside the originals because the other readers still use
the served order: 4E's single row, the eager prefill (tv_tetra48, tv_q4_hht) and the embedding gather. Dropping the
originals would need every reader on the tree tiling; that is code, never written.

Verdict: the speculative form fails b_max, by the tiled copies alone. The copies double the kernel bytes a weight.
The 4B itself fits any card: 8.7 GB at 8k is far under 32 GiB less the 5 GB margin. The failure is for the class the
triplet sizes, where the copies would cost a second set of weights. Only "no copies and a coded drafter" passes, and
both halves are unwritten.
