L01: `rhoapply` WALKS THE SERVED MIXED FILE, AND rho ON IT IS 0.929433
(2026-09-13)
================================================================================
Prereg      : `proofs/preregistration-m1-rho-2026-09-07.md`, stamped, is the one
              this tool implements; it was written for the BARE Tetra file and
              says nothing about a mixed one. Nothing is preregistered here and
              nothing needs to be: no model is scored, no arm is published. The
              MMLU arm L01 asks for has NOT run and needs an operator go.
Code        : branch claude/fine-tuning-cost-mmlu-gain-kic9ua, this commit.
              `cargo build --release -p llvq-bench --example rhoapply`
Job         : none. **0.00 $.** Mac only, no card, no bucket.
Nature      : *measured* for every figure below; the files are on disk

WHAT WAS WRONG
--------------
  `rhoapply` walked the artifact with `read_matrix_raw`, which refuses an int4
  g128 record by name (`Error::NotALatticeRecord`, `llvq-artifact/src/format.rs`).
  The served 4B is **mixed** — 216 `Tetra` records and 36 `v_proj` in int4 g128
  — so the tool died at the third record and left a truncated output file
  behind it. Eighteen record-walks in the file had the same defect.

  The fix is `read_record` / `write_record`, the only pair that can walk a
  mixed file, behind one helper (`next_raw`) that returns `None` for an int4
  record. L01's safety property then holds **by construction**: an int4 record
  has no `row_scales` for a factor to reach, so `v_proj` is never scaled
  without a name check that a renamed projection could defeat.

  One alignment trap, and it would have been a wrong file rather than a crash:
  `rho_of` is indexed by record position and `rewrite` asks for `(mi, i)`, so
  an int4 record must push an **empty** row and not be skipped. Dropping the
  entry shifts every rho after the first int4 record onto the wrong matrix.

WHAT LOCKS IT
-------------
  `llvq-artifact/tests/int4_format.rs::a_row_scale_rewrite_leaves_every_int4_byte_alone`:
  builds a Tetra/int4/Tetra file, locates the int4 record's byte span with the
  format's own walker, and asserts that a row-scale rewrite at rho = 1 is
  byte-identical and that at rho = 0.929234 **not one byte of the int4 span
  moves** while the file as a whole does. Two mutants run against it:

    M1  the rewrite also touches an int4 field   killed
    M2  rho = 1 is no longer the identity        killed

  The assertion is on bytes and not on fields: a re-serialization that produced
  equal fields through a different encoding would still be a rewritten
  `v_proj`.

WHAT THIS DOES NOT ESTABLISH
-----------------------------
  - **No quality number.** L01's cell asks for one full-split arm ($0.70 on
    L40S or ~50 min on the Mac) at the 0.43 pp bar. It has not run, and it
    needs an operator go. The +1.0 pp in the table is *computed* on the served
    base from a +1.65 pp *measured* on bare Tetra.
  - The two written arms are in a scratch directory, not published, not sealed
    and not scored.
  - The stamped prereg of 2026-09-07 was written for the bare file. Running an
    arm on the mixed file is a deviation and needs its own declaration.
  - L01 and the gain-rule shrink k = 0.96 of
    `claude/analyse-comportements-couteux-85ypbr` are the **same degree of
    freedom**: `reconstruct_shape_gain` computes `centroids[gain] * row_scale`,
    so a constant on the centroids and a constant on the row scales are one
    operation on the decoded weights. The stack's counting rule says they count
    once. Nothing here double-counts them, and nothing here has scored either.
