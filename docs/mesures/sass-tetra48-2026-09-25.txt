THE SERVED TETRA LOOP IN SASS: 241 INSTRUCTIONS A BLOCK, 10.04 A WEIGHT (2026-09-25)
=====================================================================================
Prereg  : none, and none is owed. This reads compiler output: nothing runs on a
          card and nothing about the model is measured (METHODE.md section 1,
          the same footing as references-comptabilite-2026-09-18).
Code    : commit 5d36d52. No job, no card, $0.
Tools   : NVRTC 12.4.127 (PyPI wheel nvidia-cuda-nvrtc-cu12), cuobjdump and
          nvdisasm 12.4.127 (conda channel nvidia, label cuda-12.4.1).
Data    : docs/mesures/sass-tetra48-2026-09-25-brut/
Nature  : *measured* for the static counts and the register report, read off
          the cubin; *computed* for the per-weight division. The split into
          stages is a classification by hand of each line's data dependencies,
          written line by line in `loop-annotated.txt`.

SETUP
------
Object: `tv_tetra48_h`, the one-row served kernel
(`llvq-llm/kernels/tv_tetra48_h.cu`). The translation unit is assembled as
`llvq-llm/src/fused_cuda.rs` assembles it for `Tetra48`: `TILE_BLOCKS 64u` (the
served row for sm_89, `llvq-cuda/src/tile.rs`), `TETRA48_ROWS 4u` and
`TETRA48_TILE 128u` (`Prefill::SERVED`), then llvq_slot.cuh, matvec.cu,
llvq_rot.cuh, rotate.cu, llvq_f1rank.cuh, llvq_f1rank_v3.cuh, llvq_tetra48.cuh,
tv_tetra48_h.cu, joined with "\n" (88,592 bytes, sha256 5ee214cbfa913e9c). The
emb_q8 and tv_q4_h parts are left out: they are other kernels and nothing of
them enters `tv_tetra48_h`. So this text is not the served job's NVRTC text,
whose sha256 is printed by `fusedrun`.

Compiled with `--gpu-architecture=sm_89` to a cubin (sha256 ec8e6cad8dd83cea).
The served path compiles `compute_89` PTX and the driver JITs it on the card.

Control arm: `tv_f16`, the bench's in-house FP16 control, from the same unit.

CONTROLS
---------
1. Registers: 40, stack 0, local 0. The card reports 40 for this kernel
   (`tv_tetra48_h.cu`: "the one-row kernel reports 40 registers against a
   contract of 64"). Passes.
2. `tv_f16`: 42 registers here, 42 reported by the card on 2026-09-20
   (banc-t64-2026-09-20-brut/banc.txt). Passes.
3. The loop body is exactly one block for one lane: 24 FADD (one bias removal
   a coordinate), 6 IDP.4A (one a quad), 6 LDS.128 (24 floats of activation),
   10 global loads (2 for the word, 3 rank rows, prefix, branch, suffix,
   gscale, invnorm), 25 FFMA = 24 + the one that folds invnorm into the running
   sum. Passes.
4. Tile: the same unit at `TILE_BLOCKS 128u` gives the same 241-instruction
   loop; the two listings differ only in the tile constants. Passes.
5. Determinism: two compiles give the same cubin. Passes.

RESULT
-------
`tv_tetra48_h` is 576 instructions. The inner loop runs from 0x0270 to
0x1170: **241 instructions an iteration, one iteration = one 24-weight block
for one lane, hence 10.04 a weight** (*computed*). Nothing inside the loop
branches, so the static count is also the dynamic count per block.

  stage                                  instr   memory
  A  fetch the 6-byte word                  14   2 LDG
  B  Golay path and rank rows               49   6 LDG: prefix, branch, suffix, 3 rank rows
  C  values as bytes                        64   (10 table select by p + 3 x 18 per section)
  D  byte to float                          56   (24 PRMT + 24 FADD + 8 constant moves)
  E  activation and dot                     33   6 LDS.128 + 3 address + 24 FFMA
  F  magnitude and gain                     20   2 LDG: gscale, invnorm; 6 XOR + 6 IDP.4A

`tv_f16`: the compiler unrolls its main loop by 8. **247 instructions per 64
weights, 3.86 a weight**: 64 FFMA, 64 HADD2.F32, 8 LDG.E.128, 32 LDS and 8
LDS.128, 35 IADD3, 22 SHF.L, 10 IMAD.SHL, 4 others. Both counts include one
FFMA a weight, the multiply-add any matvec pays.

AGAINST THE SOURCE-LEVEL COUNT
-------------------------------
The header of `llvq_f1rank_v3.cuh` counts ≈141 a block for `f1r_dot_v3`, by
reading the code. The served loop compiles to 241, and the 100 split in two.

34 are work `f1r_dot_v3` does not do: the magnitude and gain (20), the
activation loads and their address (9), the scale and accumulate (2), the loop
(3).

66 are what a source-level count leaves to the compiler, on the part both count:

  header item                           header   SASS
  fields, 6 loads, index arithmetic        ~26     63   (A + B: 64-bit addresses, 6-byte phase fix)
  4 table selects by p                       4     10   (the constants are materialised)
  per section, excluding the value path     39     54   (0x7777 selector masks, 3-instruction byte masks)
  8 x (PRMT, FADD, FFMA) per section        72     80   (prmt control constants)
  total                                    141    207

The header's own caveat covers two of these: `__byte_perm` inserts a LOP on
non-immediate selectors, and the served build uses the three-instruction byte
mask, not the one-`prmt` form.

WHAT THIS DOES NOT ESTABLISH
-----------------------------
- The card's SASS. The served path hands PTX to the driver, whose compiler may
  schedule or select differently. The register count agrees; the instruction
  count on the card was not read.
- Time. A static count is not a cycle count. The loop mixes 10 global loads, 6
  shared loads and several pipes, and nothing here says which one binds.
- The prefill kernel (`tv_tetra48_rows_h`, 4 rows) and the int4 kernel
  (`tv_q4_h`) are not counted, nor is `Planes14`.
- The per-row epilogue (warp_sum, tail dot, row scale, fp16 store) runs once
  per output row and is outside the 241.
