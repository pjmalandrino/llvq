LA PORTE, ET D'OÙ ELLE VIENT
----------------------------
  F1c (docs/ROADMAP.md §2.2) : encodeur ≤ 656 µs/bloc/cœur. C'est un chiffre
  d'ENCODEUR SEUL, celui de docs/HISTORIQUE.md (639 µs, `encbench`, G1-G4) ;
  `encbench 2000` rejoué le 2026-09-05 : nearest_scaled N(0,1) 680 µs,
  nearest_angular 709 µs, un cœur (*mesuré*, audit-enc/encbench-2000.txt).
  ⚠️ Ce n'est PAS le run 4B tout compris : 14 447 s × 16 fils / 150 681 600
  blocs = 1 534 µs/bloc/cœur, hessiennes et GPTQ inclus (*calculé*, fiche-4b).
  La comparaison encodeur contre encodeur est donc la bonne ; sa dérivation
  n'était écrite nulle part, elle l'est ici.

----------------------------------------------------------------------------
  Appartenance à une classe de la table universelle :
      membre ⟺ cost(ρ) < C, ou cost(ρ) = C et ρ ≤ cut (ordre lexicographique)
      cost(ρ) = Σ_j (2ρ_j + 1)²
      classe 0 : C = 88, cut (1,1,0,3,0,0,1,1), 1 256 sous C + 792 sur C
      classe 1 : C = 96, cut (0,0,2,2,2,0,1,1), 1 816 + 232
      milieu   : C = 72, cut (3,0,0,0,1,0,1,0), 1 307 + 741, N0 = 1 240
  Vérifiée contre `llvq_bench::f1::rank::RankTable::build()` sur les
  16 777 216 vecteurs de {0..7}^8 : 0 désaccord sur les trois ensembles
  (*mesuré*, f1encaudit). Fait trouvé par la relecture : (2ρ+1)² ≡ 9 mod 16
  ssi ρ ∈ {1, 2}, donc classe = [cost ≡ 0 mod 16] — le test de classe est
  redondant avec le coût, 0 violation sur {0..4}^8.
  Équivalence avec le banc : 307 200 résolutions (cible, p, motif, parité),
  0 désaccord de distance, 0 point différent à distance égale.

  (8 rétrécissements) 242 ns ; tronquée à 3 rétrécissements 143 ns ; contre

CE QUI EN SORT
--------------
  · 290-296 µs/bloc/cœur contre 656 : 0,45× la porte (*mesuré*, trois runs).
    Sur le 4B (150 681 600 blocs, 12 fils) : ~62 min d'encodage seul
    (*calculé*). 814× plus vite que le banc, dont 9× d'échelles en moins et
    ~90× par (bloc, échelle).
  · L'option « 3 échelles tronquées » est À la porte (650-662), pas dessous.
  · Le prototype reproduit le banc point pour point : il n'introduit aucune
    perte ; la perte de 0,16 pp est celle du nombre d'échelles.

CE QUE ÇA NE DIT PAS
--------------------
  · Des blocs N(0,1), pas des poids. L'élagage (188 résolutions sur 1 536)
    dépend du taux « base membre » (58 % ici à l'échelle adaptative, 0 % à
    s = 0,10). Sur des résidus GPTQ tournés il n'est PAS mesuré ; l'exhaustif
    à 2 échelles vaut 962 µs, au-dessus de la porte. C'est l'hypothèse la plus
    dangereuse, et la première chose à mesurer (0 $, un dump de blocs du 0,6B).
  · « −0,16 pp » n'est pas un critère de F1c. La porte de F1c est en
    perplexité ; sa forme (appariée par graine, ρ fixé, prédiction signée)
    est à l'opérateur.
  · Le prototype porte sa propre copie de la table de rangs
    (f1enclazy.rs:94-130) ; la comparaison au module `f1::rank` est faite
    pour la table (f1encaudit), pas encore pour l'encodeur.
  · La clé de rang empile ρ₀ en poids fort dans le prototype, en poids faible
    dans `rank::pack` : une convention à unifier à la mise en production.
