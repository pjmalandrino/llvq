Result: one memory gain is certain and keeps every bit: the file can lose about 38 MB, 2.8206 to about 2.745 b/param
of file bytes, with the card unchanged (*computed*). The VRAM gains that keep every bit are uncertain, 0 to 0.55 GB,
because 0.53 GB of the 1.98 GB after load is fixed overhead nobody has split (*computed* as a difference). The only
large VRAM gain is the chain prefill: 5.95 to 3.56 GB at 8k and a first token 2.8 to 4.7 times sooner (*measured*,
bench). It does not keep the text: 41 of 47 texts identical, It is a gated change.

Nature: read-only study. No job, no build, no test, no model load. Code read at 435d48f (worktree arbre-nuit), journals
named on each line. GB = 1e9 B. Parameters 4,022,468,096 (rtbits). Labels: *measured* (a journal), *computed*
(arithmetic on measured or code inputs), *estimated* (judgement, or one estimated input).

2.76 and the 14B 5.637 for 5.04 (*measured*, served-v9 jobs): the gap is 0.60 at all three, so it scales with nothing
the model holds. Of it, 0.53 is there before 4E is installed, It belongs to the context and the libraries.
Nobody has measured the context alone (no cuMemGetInfo before the weights exists in any journal).

File against card: the file is 1,418,224,685 B, 2.8206 b/param (*measured*, ~/q4b-sealed-2026-09-23 listing; duel-iq2
uses this figure). The card holds 1.38 GB, 2.73 b/param. The file carries three things the card does not: the tail in
f32 (+29.3 MB over the card's f16), the row scales in f64 (+3.8 MB over the card's f32), and config.json plus

Left out, with the reason:
- Eager prefill in chunks of 2,048: -1.07 GB at 8k, but cuBLAS rounds by shape (gqa-ab-2026-11-01), so the bits move.
- Kernel prefill (`prefill_attention: kernel`): 4.77 GB at 8k, over its band, first token x1.14 to x1.21 slower
  (pic-vram-8k G3). Not served, and #2 dominates it.
- KV cache in int8 or int4: touches quality (ETAT section 5). The f16 KV is 1.21 GB of the 8k peak and stays.
- KV growth policy: Grow(256) leaves at most 37.7 MB unused, and a growth copies one layer at a time and syncs
  (model.rs:474-489). Nothing to gain.
- Embedding and head tie: already one table on the card.
- Duplicates between eager and 4E: none at steady state (section 1).
- Lossless coding of the Tetra words: closed (47.4 bits of entropy of 48).

3. WHAT I WOULD DO FIRST
------------------------
First, the file trim (#1). It is the only gain that is both certain and identical on every door: about -0.076 b/param
of file bytes, which turns today's tie with llama.cpp IQ2_S on the duel's accounting (2.8206 against 2.8188) into a
lead of about 0.07. It costs a format revision and a riding gate. Second, the $0 ledger riding the next card job, then
#3 and #4 if it points at them. Those are the only VRAM gains that keep every bit, worth 0 to 0.55 GB, and nobody knows
which end of that range is real until the ledger runs. No VRAM gain that keeps the text is certain today. The large
one, the chain prefill (#2), is worth doing for the first token as much as for memory, but it changes 6 texts in 47 on
near-ties: it is the operator's call whether the +-0.12 % band counts as "no trade-off".
