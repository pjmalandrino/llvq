\section{From the codebook to a served file}
\label{sec:model}

A served file holds more than lattice codes, the indices that encode each block
of weights. Below we list what else it holds, then the three changes that
produce the files we measure. None of them changes a lattice code or the
decoder.

\subsection{What a file holds, and how we count it}
\label{sec:file}

Each layer of Qwen3~\citep{qwen3_2025} has seven projection matrices: $q$, $k$,
$v$ and $o$ in attention, and gate, up and down in the feed-forward block. The
4B and 8B models have 36 layers (252 projections), and the 14B has 40 (280).

Each projection is stored as \Tetra{} blocks or as an int4 record. An int4
record holds 4-bit weights in groups of 128, with an f16 scale and offset per
group, read by a separate GPU kernel. A \Tetra{} projection also stores one
scale per output row. It keeps a small tail exactly, in f16: the weights at the
end of each row that do not fill a whole block. The RMSNorm weights (the
per-channel scales of the normalization layers) stay in f16. The embedding
table is stored separately, and so is the output head at 8B and 14B. At 4B the head reuses the embedding table (a tied head).

We count memory in bits per parameter over the whole model. It is all the
weight bits the served model keeps, divided by the number of parameters. This
includes the embedding, the tail, the scales and the int4 records. One tool
computes it from the file for every object in this paper. We do not count the KV cache (the
attention memory that grows with the context) or the activations.

\subsection{Training the row scales}
\label{sec:rowscales}

Equation~\eqref{eq:recon} multiplies each reconstructed output row by one
scale, $\sigma_{\mathrm{row}}$, which the encoder fits by least squares. We
retrain only these scales, with the FP16 model as teacher~\citep{hinton2015}.
On DCLM-edu text~\citep{dclmedu}, a KL loss pulls the quantized model's output
probabilities toward the teacher's. The lattice codes stay fixed and no bit is
added: the trained scales replace the old ones in place. At 4B the training
sees 19.5 million tokens and takes 1.7~h on one L40S GPU. The 8B and 14B runs
take 1.1~h and 2.0~h on one H200. This step alone adds 3.15, 3.29 and 1.67 MMLU
points at 4B, 8B and 14B (\S\ref{sec:chain}).

\subsection{int4 where the lattice loses the most}
\label{sec:int4}

Some projections lose more accuracy than others on the lattice. Every file
stores \texttt{v\_proj} in int4. Under grouped-query attention, several query
heads share one key and value head, so the $v$ matrices are small. At 4B,
moving them from \Tetra{} to int4 gained 3.47 MMLU points on our
2{,}280-question sample for 0.05 bits per parameter.

We call the three files we serve \emph{sealed}. They also store
\texttt{o\_proj} in int4, and \texttt{down\_proj} in a range of middle layers
(Table~\ref{tab:files}). At 8B only \texttt{down\_proj} is added, and
\S\ref{sec:chain} explains why.

\subsection{4-bit embedding tables}
\label{sec:q4emb}

Qwen3's vocabulary has 151{,}936 entries, so the embedding table is 9.7\,\% of
the parameters at 4B. At 8B and 14B the output head is a second table of the
same shape. Together they are 15.2\,\% of the parameters at 8B and 10.5\,\% at
14B. Before this step, our files stored these tables in 8 bits. The sealed
files store them in 4 bits, in groups of 64 with an f16 scale and offset per group, as MLX
does~\citep{mlx2023}. The GPU dequantizes rows on the fly, when it looks up
input tokens and inside the matrix-vector product of the head. Going from 8 to
4 bits frees 0.19~GB at 4B, 0.62~GB at 8B and 0.78~GB at 14B. This saving pays
for the int4 projections: every sealed file needs fewer bits per parameter than
the file it was built from (\S\ref{sec:chain}).
