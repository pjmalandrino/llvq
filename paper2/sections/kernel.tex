\section{The kernel}
\label{sec:kernel}

\subsection{Decoding inside the matrix-vector product}

The kernel keeps the thread layout of our earlier one~\citep{llvq1preprint}.
One warp (threads that run in lockstep) computes each output row, and a
256-thread block holds 8 rows. Each thread of the warp, or lane, decodes one
block of weights at a time. The activation goes into shared memory, a small
fast on-chip memory, in tiles of $T$ blocks ($96T$ bytes). Each tile has two
barriers, where all threads wait. A shuffle reduction sums the lanes' results,
and a last step adds the exactly kept tail and multiplies by
$\sigma_{\mathrm{row}}$. What differs is how a block is decoded.

Decoding a block takes six table loads, and three choices make it fast. First,
each table value is stored as a biased byte, $\mathrm{val}+128$. Placed in the
low byte of \texttt{0x4b0000\_\_}, it reads exactly as the float
$2^{23}+\mathrm{byte}$, and one subtraction gives the value back. A coordinate
thus costs one byte permute (a byte move inside a register), one add and one
fused multiply-add, with no integer-to-float conversion. Second, every loop is
unrolled with constant indices, so no value spills from registers to the slower
local memory. The compiler reports 40 registers and no local memory, as for
\Planes{}. Third, the only reads that depend on the data are the six table
loads, so the lanes never take different paths.

Counted from the source, a block costs about 141 instructions: 54 on the FMA
pipe (the multiply-add unit) and 85 on the ALU pipe (the integer and bit
unit). A decoder that extracts and converts each coordinate needs about 380,
plus 24 conversions.

The kernel reads the file's 48-bit words as stored, so nothing is rewritten at
load.
In the same process, the 4B file loads in 12.1~s and its dense reconstruction
(the file decoded to f16) in 81.8~s.

\paragraph{The rest of a served model.} The int4 projections use a separate
kernel with the same thread layout. It copies the whole activation into shared
memory, dequantizes each weight with its group's scale and offset, and
accumulates in f32. At 14B, a \texttt{down\_proj} activation takes
69{,}632~B, more than the 48~KiB a thread block gets by default, so the CPU
code asks the driver for more. The L40S allows 101{,}376~B. The 4-bit
embedding tables use two small kernels: one looks up and dequantizes the input
tokens' rows, the other is the output head's matrix-vector product. On a
prompt, the \Tetra{} kernel takes four tokens per launch, the int4 kernel one
at a time.

\paragraph{How the kernel is checked.} Before any timing, we recompute all
1{,}105{,}920 output rows of the 4B model in f64 from the same decoded
weights. Each must match the kernel's row within
$10^{-5}\cdot\sum|w\cdot x|$. The worst \Tetra{} row is off by
$2.1\times10^{-8}\cdot\sum|w\cdot x|$. One level down, we compare the GPU
decoder's outputs with an independent CPU implementation, on the development
machine and again on the card. For each 48-bit word, the 24 decoded values
must match bit for bit. End to end, each served model and its dense reconstruction
generate 256 greedy tokens (always the most likely next one) in the same
process. We compare the two sequences (\S\ref{sec:main}).

\subsection{The tile and the L1 cache}
\label{sec:tile}

On an Ada GPU (sm\_89), each streaming multiprocessor (SM) splits one 128~KB
pool of on-chip memory between the L1 cache and shared memory, with at most
100~KB for shared memory~\citep{cudaguide}. The activation tile lives in shared
memory. The decoder tables are ordinary memory reads, cached in L1. So the tile
size, which changes no output bit and costs no storage, decides how much L1 is
left for the 18.4~KiB of tables.

Occupancy, the number of thread blocks an SM holds at once, does not change
with the tile. Both lattice arms launch 256 threads per block at 40 registers
per thread, so six thread blocks fit at every tile
($6\times256\times40 = 61{,}440$ of 65{,}536 registers). Shared memory is never
the binding limit ($6\times12{,}288 < 102{,}400$~B). Besides the L1 split, the
tile changes how often each row loops and waits at a barrier, the same for all
arms.

Across $T \in \{128, 64, 32\}$, the \Planes{} time varies by 1.5\,\%, the
no-weights time by 5.1\,\% and the \Tetra{} time by 19.1\,\%
(Figure~\ref{fig:tile}). The three arms share the thread layout, the activation
copy and the occupancy. Only the \Tetra{} arm reads tables. We think the
difference comes from pressure on the tables' room in L1, but we have not
proven it. Our rented platform gives no access to performance counters, so we
measured no cache hit rate. We set the served tile to $T=64$ on sm\_89. On an
sm\_120 card the same sweep prefers $T=32$, so the best tile depends on the
card, not on the format. All other kernel numbers in this paper are at $T=64$.
