\section{The kernel}
\label{sec:kernel}

\subsection{Decoding inside the matrix-vector product}

The kernel keeps the geometry of our earlier one~\citep{llvq1preprint}: one
warp per output row, 256-thread blocks holding 8 rows, the activation staged in
shared memory in tiles of $T$ blocks ($96T$ bytes) with two barriers per tile,
one lane per block, a shuffle reduction, and a last step that adds the
exactly-kept tail and multiplies by $\sigma_{\mathrm{row}}$. Only the decode
changed.

Three choices make a six-load decode fast. First, table values are stored as
biased bytes, $\mathrm{val}+128$. Placed under \texttt{0x4b0000\_\_}, such a
byte reads as the float $2^{23}+\mathrm{byte}$ exactly, and one subtraction
gives the value back, so a coordinate costs one byte permute, one add and one
fused multiply-add, with no integer-to-float conversion. Second, every loop is
unrolled with constant indices, so nothing spills: the compiler reports 40
registers and no local memory, the same as for \Planes{}. Third, the only
data-dependent reads are the six table loads, so lanes never diverge. Counted
from the source, a block costs about 141 instructions, 54 of them on the FMA
pipe and 85 on the ALU pipe. A decoder that extracts each coordinate and
converts it needs about 380, plus 24 conversions.

The kernel reads the file's own words, so there is no transcoding at load. The
4B file loads in 12.1~s, where the FP16 checkpoint takes 81.8~s in the same
process.

\paragraph{The rest of a served model.} The int4 projections go through a
separate kernel with the same geometry: one warp per row, the whole activation
staged in shared memory, weights dequantized with their group scale and offset,
accumulation in f32. At 14B a \texttt{down\_proj} activation takes 69{,}632~B,
more than the 48~KiB a block gets by default, so the host asks the driver for
more; the L40S allows 101{,}376~B. The 4-bit embedding tables use two small
kernels, a gather that dequantizes the rows of the input tokens and a
matrix-vector product for the output head. For a prompt, the \Tetra{} kernel
takes four rows per launch; the int4 kernel takes them one at a time.

\paragraph{How the kernel is checked.} Before any timing, each of the
1{,}105{,}920 output rows of the 4B model is recomputed in f64 from the same
decoded weights and compared with the kernel's row, at a threshold of
$10^{-5}\cdot\sum|w\cdot x|$. The worst \Tetra{} row is at
$2.1\times10^{-8}\cdot\sum|w\cdot x|$. One level down, the 24 outputs of the
device decoder are compared bit for bit with an independent host implementation
of the same word, on the development machine and again on the card. End to end,
each served model generates 256 greedy tokens next to its dense reconstruction
in the same process, and the two sequences are compared (\S\ref{sec:main}).

Per weight, \Tetra{} reads 2.148 bits where 4-bit AWQ reads 4.179 and \Planes{}
reads 4.804: about half the traffic of either (Table~\ref{tab:bench}). The
milliseconds do not rank the arms, for the reason given in the caption. They do

\Tetra{} runs at 278~GB/s where AWQ reaches 583, so it is limited by decoding
more than by memory traffic.

\subsection{The tile and the L1 cache}
\label{sec:tile}

On an Ada SM (sm\_89), L1 and shared memory share one 128~KB block of SRAM, of
which at most 100~KB can go to shared memory~\citep{cudaguide}. The activation
tile is shared memory. The decoder tables are not: they are ordinary global
reads, cached in L1. So the tile size, which changes no output bit and costs no
storage, decides how much L1 is left for 18.4~KiB of tables.

Occupancy does not change with the tile. Both lattice arms launch 256 threads
at 40 registers, so six blocks are resident at every tile
($6\times256\times40 = 61{,}440$ of 65{,}536 registers), and shared memory is
never the binding limit ($6\times12{,}288 < 102{,}400$~B). What the tile does
change, besides the split between L1 and shared memory, is the number of
barriers and loop trips per row, and that part is common to all arms.

Across $T \in \{128, 64, 32\}$ the \Planes{} arm moves by 1.5\,\%, the
no-weights kernel by 5.1\,\% and the \Tetra{} arm by 19.1\,\%
(Figure~\ref{fig:tile}). The three arms share the launch geometry, the staging
code and the occupancy; only the \Tetra{} arm reads tables. We read the
difference as pressure on the tables' place in L1 and set the served tile to
$T=64$ on sm\_89. We have not proven that reading: the rented platform denies
access to performance counters, so no cache hit rate was measured. On sm\_120
the same sweep prefers $T=32$, so the best tile belongs to the card rather
than to the format. All other kernel numbers in this paper are at $T=64$.
