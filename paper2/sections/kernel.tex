\section{The kernel}
\label{sec:kernel}

\subsection{Decoding inside the matrix-vector product}

The kernel keeps the thread layout of our earlier one~\citep{llvq1preprint}.
One warp (threads that run in lockstep) computes each output row, and a
256-thread block holds 8 rows. Each thread of the warp, or lane, decodes one
block of weights at a time. The activation goes into shared memory, a small
fast on-chip memory, in tiles of $T$ blocks ($96T$ bytes). Each tile has two
barriers, where all threads wait. A shuffle reduction sums the lanes' results,
and a last step multiplies by $\sigma_{\mathrm{row}}$ and adds the unquantized
tail. What differs is how a block is decoded.

Decoding a block takes six table loads and two small lookups, for the gain and
the norm. Three choices make it fast. First, each coordinate value is held in a
register table as a biased byte, $\mathrm{val}+128$. Placed in the
low byte of \texttt{0x4b0000\_\_}, it reads exactly as the float
$2^{23}+\mathrm{byte}$, and one subtraction gives the value back. A coordinate
thus costs one byte permute (a byte move inside a register), one add and one
fused multiply-add, with no integer-to-float conversion. Second, every loop is
unrolled with constant indices, so no value spills from registers to the slower
local memory. The compiler reports 40 registers and no local memory for the
benchmark kernel, as for \Planes{}. Third, no branch depends on the data, so
the lanes never take different paths.

Counted from the source, the rank decode and the 24 multiply-adds of a block
take about 150 instructions: about 60 on the FMA pipe (the multiply-add unit),
about 85 on the ALU pipe (the integer and bit unit) and six loads. The gain and
the norm add about 20. A decoder that extracts and converts each coordinate
needs about 380, plus 24 conversions.

The kernel reads the 48 bits the file stores for each block, and no code is
expanded. Loading only reorders the bits of each word and pads each row to a
multiple of 8~bytes. In the same process, the sealed 4B file loads in 4.1~s
and its dense reconstruction (the file decoded to f16) in 72.9~s.

\paragraph{The rest of a served model.} The int4 projections use a separate
kernel with the same thread layout. It copies the whole activation into shared
memory, dequantizes each weight with its group's scale and offset, and
accumulates in f32. At 14B, a \texttt{down\_proj} activation takes
69{,}632~B. That is more than the 48~KiB a thread block gets without an
explicit opt-in, so the CPU code asks the driver for more. The L40S, of
compute capability 8.9, allows at most 101{,}376~B, or 99~KiB~\citep{cudaguide}. The 4-bit
embedding tables use two small kernels: one looks up and dequantizes the input
tokens' rows, the other is the output head's matrix-vector product. The
activations are rotated online to match the rotated weights. At 4B, a small
kernel runs 96 times a token, once per group of projections that share a
rotation. On a
prompt, the \Tetra{} kernel takes four tokens per launch, the int4 kernel one
at a time.

\paragraph{How the kernel is checked.} Before any timing, we recompute every
output row of the 4B shapes in f64 from the same decoded weights: 1{,}105{,}920
rows, 1{,}069{,}056 of them for the 216 \Tetra{} matrices. Each must match the
kernel's row within $10^{-5}\cdot\sum|w\cdot x|$, or $10^{-3}$ for the two
arms that write f16, AWQ and cuBLAS. The worst \Tetra{} row is off by
$2.1\times10^{-8}\cdot\sum|w\cdot x|$. One level down, the decoder's CUDA
source, compiled for the CPU of the development machine, must give the 24
lattice coordinates of each 48-bit word bit for bit against an independent
Rust decoder. On an sm\_120 card, the scaled values of 1{,}792 blocks match
that decoder within a relative $10^{-5}$. End to end, each served model and its dense reconstruction
generate 256 greedy tokens (always the most likely next one) in the same
process. We compare the two sequences (\S\ref{sec:main}).

Per weight, \Tetra{} reads 2.148 bits, against 4.179 for 4-bit AWQ and 4.804
for \Planes{}, about half the bytes of either (Table~\ref{tab:bench}). The
\Tetra{} arm covers fewer matrices, so its time is a lower bound for the full
set. Even so, it is slower than the AWQ arm: 3.424 against 3.261~ms. The
no-weights kernel takes 2.289~ms, and \Planes{} 4.997~ms. \Tetra{} reads its bytes at 278~GB/s,
where AWQ reaches 583. Reading half the bytes does not halve the time.

\subsection{The tile and the L1 cache}
\label{sec:tile}

On an Ada GPU (sm\_89), each streaming multiprocessor (SM) splits one 128~KiB
pool of on-chip memory between the L1 cache and shared memory, with at most
100~KiB for shared memory~\citep{cudaguide}. The activation tile lives in shared
memory. The decoder tables are ordinary memory reads, cached in L1. So the tile
size, which changes no output bit and costs no storage, decides how much L1 is
left for the 18.4~KiB of tables.

Occupancy, the number of thread blocks an SM holds at once, does not change
with the tile. Both lattice arms launch 256 threads per block at 40 registers
per thread, so six thread blocks fit at every tile. Six blocks are the
1{,}536 threads an sm\_89 SM can hold, and they use 61{,}440 of its 65{,}536
registers~\citep{cudaguide}. Shared memory is never
the binding limit ($6\times12{,}288 < 102{,}400$~B). Besides the L1 split, the
tile changes how often each row loops and waits at a barrier, the same for all
arms.

Across $T \in \{128, 64, 32\}$, the \Planes{} time varies by 1.5\,\%, the
no-weights time by 5.1\,\% and the \Tetra{} time by 19.1\,\%
(Figure~\ref{fig:tile}). The three arms share the thread layout, the activation
copy and the occupancy. \Planes{} reads one entry per block from a 12~KiB
class table. \Tetra{} reads seven from its 18.4~KiB of tables. We think the
difference comes from pressure on the tables' room in L1, but we have not
proven it. Our rented platform gives no access to performance counters, so we
measured no cache hit rate. We set the served tile to $T=64$ on sm\_89. On an
sm\_120 card, an earlier sweep on other 4B files puts \Tetra{} fastest at
$T=32$ and \Planes{} fastest at $T=128$. The best tile depends on the card and
on the kernel. All other kernel numbers in this paper are at $T=64$.
