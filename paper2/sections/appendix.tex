\section{Record of trials, predictions and commands}
\label{app:record}

\textbf{Predictions, and how they scored.} Before the tile sweep we
preregistered a \Tetra{} time of 3.77~ms $[3.5, 4.1]$ at $T=64$ and a gain of
$+8.3\,\%$ $[0, +15]$; we measured 3.423~ms and $+16.1\,\%$, both outside their
intervals, in the favourable direction. Before the first row-scale training we
preregistered $+1.0$~pp $[-0.5, +2.5]$ of MMLU, then revised it down to $+0.4$
because the training curve was flat; we measured $+4.30$. The revision was
wrong for an instructive reason: we had read a 7.5\,\% fall in KL on held-out
text as a small effect, and KL on a calibration corpus and MMLU do not scale
together.

\textbf{The tile.} It is a constant injected by the host at compile time.
Every figure we published before 2026-09-20 was measured at $T=128$. The served
default is now whichever tile was measured fastest on that card, 64 on sm\_89
and 32 on sm\_120, falling back to 128 on a card we have not swept; every
benchmark prints which value it used.

\textbf{The segmented kernel.} A variant fusing $q{+}k{+}v$ and
$\mathrm{gate}{+}\mathrm{up}$ into single launches is written, compiles on the
card and passes four host-side tests, and fails the bit-exact comparison
against the unfused arm. It is behind \texttt{LLVQ\_SEG\_TETRA}, off by
default, and no number in this paper comes from it.

\textbf{Identity checks.} The object of \S\ref{sec:results}: 32 greedy tokens
identical to the FP16 checkpoint's (dclm-ft-fusedrun-2026-09-20). An earlier
\Tetra{} object of 2026-09-10: 256 tokens (f1e0-2026-09-10). Both journals also
record an \texttt{oracle} match; that binary compares our forward
implementation with \texttt{candle-transformers} on an unquantized checkpoint
and is not evidence about the kernel.

\textbf{The object and the commands.} \texttt{qwen3-4b-dclm-ft.bin},
1{,}794{,}564{,}765~B, \texttt{sha256 f8c1c903b753fe34\ldots}. On an NVIDIA
GPU:

{\footnotesize
\begin{verbatim}
LLVQ_CONFIG=configs/qwen3-4b-tetra-q5.json cargo run --release \
  -p llvq-llm --features cuda --bin fusedrun -- <sealed>      # tok/s, GB
cargo run --release -p llvq-cuda --bin planesbench -- <sealed> # Table 1
LLVQ_DTYPE=f16 cargo run --release -p llvq-llm --features cuda \
  --bin ppl -- 4096 12 cuda <sealed>
cargo run --release -p llvq-llm --features cuda --bin mmlu -- <sealed> cuda 40
\end{verbatim}}

\noindent\texttt{LLVQ\_FUSED\_LAYOUT=tetra48} selects the layout;
\texttt{LLVQ\_TILE\_BLOCKS} overrides the tile and defaults to the measured row
for the card. Each binary prints a fingerprint of the scored tokens, and
numbers compare only when fingerprints match.

\textbf{Protocol notes.} A quotient of two minima gave $2.19$ on one run where
the round-by-round median gave $2.14\times$ $[2.10$--$2.16]$; three invocations
of one unmodified binary gave $2.029$, $2.050$ and $2.080\times$ at identical
bytes and identical errors, so an effect of a few percent is not settled
between two invocations. Ratios are never divided across cards or inference
stacks; memory comparisons are stated in b/param over the whole model,
embedding included. A benchmark must read more distinct bytes than the card's
L2 or it measures the cache: the lightest arm here reads $9.4\times$ the L2 per
pass.
